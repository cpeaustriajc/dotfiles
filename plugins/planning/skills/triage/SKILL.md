name: triage
description: >
  This skill should be used when the user says "triage #42", "what needs my attention", "can an
  agent take this", "move #42 to ready-for-agent" or "write an agent brief". It sets one state and
  a brief. Design questions: grill.
---

Give each issue or PR one state and one category (`bug`, `enhancement`):

| State | Means |
|---|---|
| `needs-triage` | Not checked. |
| `needs-info` | Waits on the reporter. |
| `ready-for-agent` | An agent can finish and prove it alone. |
| `ready-for-human` | A person must do a named part. |
| `wontfix` | Built already, or rejected. |

Use the team's labels; with none, propose these. No item named, or a direct order:
`references/requests.md`.

Paths are relative to this skill's folder.

## Setup

When the project's skills folder has no copy of this skill, set up first:

1. Find the tracker and what reaches it: a pointer in the instruction file, the remote, the
   connected tools' lists, the CLI's `--help`. With none installed, list the commands you would
   run and ask me to run them.
2. Write the copy in that folder: this file without Setup, every file the copy uses directly or
   through another file (copied into its folder, paths rewritten), and a description with only
   the triggers it serves. Map each state to the tracker's own field: the team's workflow status,
   else a label named for the state, created only after my yes. Add the commands to read an item
   and its comments, list open PRs with their authors' association to the team, set a state, post
   a comment and close as not planned. Put `# <plugin> <version>` (from the marketplace manifest or
   this skill's version folder) on the line after the opening `---`. Commit it alone under the
   project's branch rules, else on a new branch, with hooks on.
3. Run the copy from its Steps section.

## Steps

In every tracker: a bare `#42` can be an issue or a PR, so check which. An outside author is
one with no role in the team. "A reply after the last triage note" compares the last comment's
date with the disclaimer's and the reporter's last comment. Every write notifies watchers: set
labels and post the comment in one pass per item.

1. Read everything. An earlier triage comment's answers stay settled.
2. Search code, harness, skills, the decision log and closed `wontfix` by concept; show matches.
3. Reproduce a bug, or run a PR's checks: confirmed (code path), not reproduced or vague
   (`needs-info`), or blocked (`needs-triage`, say why). Write checks only for a confirmed bug: an unproven check passes on unchanged code.
4. `ready-for-human` if a check needs a merge, sign-in, secret, device, vendor console, paid
   account or taste. Name each.
5. Recommend in chat: state, category, a three-line reason, where you searched, the repro.
   Open scope questions go to `grill`; open behaviours in a drafted set, to `refine`. Wait for
   my go.
6. Set labels; post one comment opening `> *This was generated by AI during triage.*`, in its
   state's form from `references/agent-brief.md`. Writes follow `references/top-down.md`
   ("Write, then check the tree").
